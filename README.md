# dsh-mtool-translate

把 MTool 导出的 `ManualTransFile.json` 交给当前配置的模型翻译，产出 MTool 能直接加载回来的 JSON。
不装 AiNiee、不配第二套 API Key、不跑 Python——**只要 MTool + DSH**。

MTool 的收费翻译链路本来就是：导出原文 → 送翻 → 加载译文。这个插件只替换中间那一步。

## 安装

```bash
git clone https://github.com/wooyoojoo/dsh-MTool-translate.git
cd dsh-MTool-translate
pnpm install --prod     # 配置表单依赖 @deepseek-ai/schemastery
```

然后在 DSH 里「插件 → 添加插件」选择该目录。`pnpm install` 不能省：profile 安装 linked 包时不会替它装依赖，缺了 schemastery 插件会加载失败。

## 用法

1. MTool 里打开游戏，`翻译` → `导出游戏原文`，游戏根目录出现 `ManualTransFile.json`。
2. 把该文件拖进 DSH 对话，说「翻译这个」。
3. 助手调用 `translate_mtool_file`，产出 `ManualTransFile.translated.json`（与原文同目录，`indent=4`、不转义非 ASCII，和 AiNiee 的写出格式一致）。
4. 回到 MTool，`翻译` → `加载翻译文件`，选 `ManualTransFile.translated.json`。

再翻一次同样的文件不会重复花钱：已翻译的行、以及缓存里有的行都会跳过。

没有现成游戏想先试试：`samples/ManualTransFile.json` 是一份带控制码的小样。

> 从聊天窗口拖进来的文件会落在 DSH 的附件目录，产出也写在那儿。想让它落在工作目录里，调用时传 `outputPath`。

## 工具参数

| 参数 | 说明 |
| --- | --- |
| `path` | 必填，`ManualTransFile.json` 的路径 |
| `target` | 目标语言，默认 `简体中文` |
| `glossary` | 术语表，`"原文=>译文"` 数组，也可以传 JSON 文件路径 |
| `outputPath` | 输出路径，默认 `<输入>.translated.json` |
| `limit` | 本次最多翻多少行，用来先跑个小样 |
| `maxBatches` | 本次最多发多少个请求，剩下的下次再跑 |
| `force` | 连已有译文的行也重翻 |
| `dryRun` | 只统计待翻/缓存/已完成/跳过多少行，不调用模型 |

## 从 AiNiee 搬过来的部分

代码是按文件逐个搬的行为，不是重写：

| 文件 | 搬了什么 |
| --- | --- |
| `Backend/resources/regex/regex.json` | 50 多条 RPG Maker / Wolf / KRKR 控制码正则，顺序照抄 |

| `Backend/domain/text/filters/general_text_filter.py` | 跳过规则：纯数字、空行、纯标点、文件后缀、代码前缀 |

| `Backend/domain/responses/response_extractor.py` | `<textarea>` + `N.译文` 回包解析、丢弃序号前的废话 |
| `Backend/domain/responses/advanced_checks.py` | 占位符是否齐全、换行符数是否一致、返回原文 / 翻译残留判定 |

自己写的部分只有壳：DSH 工具注册、模型线路、分批并发、缓存、断点落盘、文件读写。

## 和 AiNiee 的差异

已经对齐的（这些以前不一样，现在一致）：

- 系统提示词用 `common_system_zh.txt` 原文；用户消息是 `###上文内容 + ###这是你接下来的翻译任务，原文文本如下 + <textarea>` 外壳。
- 多行条目用 `N.[ "N.k.,行", … ]` 子编号块发出、按块收回。
- 数字序号 `1.` 先转 `【1】` 再还原，避免和多行协议的序号打架。
- 回包序号必须是 1..n 连续递增（同 `check_dict_order`），错行直接重试而不是硬塞。
- 控制码正则表与 `regex.json` 逐条一致（54 条，脚本比对过）。
- 译前/译后替换支持正则行（`{src, dst, regex: true}`），也兼容纯字符串表。
- 禁翻表支持整行精确匹配和正则，且只把当前批次实际命中的词条发给模型。
- 角色表 / 背景设定 / 翻译风格 / 翻译示例按 AiNiee 的段落格式拼进系统提示词。
- `promptPreset: cot` 用 `cot_system_zh.txt`；`targetPlatform: sakura` 时占位符改成 `↓` 连写。
- 多行块里模型给每行都加引号时，按原文首尾字符决定保留或去掉（stage 4）。

还没对齐 / 不打算搬的：

- **回包兜底**：AiNiee 只认 `textarea + N.`；这里多留了一个 JSON 数组兜底（模型不听话时救急）。
- **占位符上限**：AiNiee 单请求最多替换 50 个占位符，超过就不再遮蔽；这里不设上限（长批次更安全）。
- **批次划分**：AiNiee 由任务调度器切块；这里按「200 行 / 6000 字」贪心打包，默认 8 并发。
- **校验口径**：「返回原文」在 AiNiee 里是整批 Jaccard ≥ 0.85，这里是逐行按原文非汉字字符覆盖率 ≥ 0.9（因为这里逐行重试）。「翻译残留」同理。这两项都默认关。
- **没搬**：术语表自动抽取（AiNiee 的 analysis 任务）、由分析任务生成的项目级角色表/术语表/禁翻表、EPUB 标记、`local` 提示词、`{p}` 复合占位的 padding 变体（套 `\s*…\s*` 会把换行一起吞掉，实测会破坏换行校验）。
- **没有 GUI**：AiNiee 的 Qt 界面、配置面板、术语表编辑页都由 DSH 对话取代。

## 配置

**在界面里改**：设置 → 插件 → `dsh-mtool-translate`（点进 bundle 页面，表单在描述和插件行之间）→ 改完点「保存」，**下次翻译立即生效，不用重启**。

页面上一共五项：

- **推理强度**：`off` / `low` / `high` / `max`（默认 `low`）。`off` 快 7 倍（1000 行 7.5s vs 52s），但逐行对照后只能当草稿档：对白里的 `「` 会被改成 `“`（114 行里 92 行）、26 条多行文本里 23 条被塞进多余的引号逗号（游戏会原样画出来）、21 行凭空补了收尾引号、17 行丢了开引号，还会误判词义（`我慢汁`=前列腺液，被译成“忍不住汁液”）。对白用 `low`，`off` 只适合没有引号/换行的短 UI 串
- **批次行数**：每请求的**行数上限**（默认 `200`），是上限不是目标——真正决定一次装多少行的是下面两条
- **单请求字数**：每请求的**字数上限**（默认 `8000`）。实测它比行数更常先绑住：200 行、每行 24 字，行数上限 200 没动，是 2400 字的旧值把它们切成了两批
- **并发**：同时在飞的请求数（默认 `8`）——实测每行耗时随批宽上升，吞吐靠并发而不是批宽，撞限流就调低
- **回复上限**：单请求 `maxTokens`（默认 `16384`）。它现在同时是**回复预算**的来源：一次请求实际装多少行 = `maxTokens × 0.75 ÷ 每行输出 token 估算`，不同推理强度用的估算值是 `off 16 / low 48 / high 64 / max 80`（实测 200 行：`off` 12.6 token/行、`low` 48.5 token/行）。所以 `low` 下 16384 大约装 256 行，而 `off` 下能装 768 行——**同一份设置，开不开思考，一次能装的行数差 4 倍**。已实测 `20000` 被服务端接受，所以旧默认 8192 是自己设的绳

> 三条上限取最小值生效。想真正降请求数就调这儿，但注意：批越宽，一次失败作废的行越多——报告里的 `retry` / `bisect` / `truncated` 就是给你看这个的。

其余都是代码里的固定值，故意不给旋钮：

| 项 | 固定行为 |
| --- | --- |
| 源语言 | 从文件内容自动判断（假名→日语、谚文→韩语、西里尔→俄语、汉字→中文、否则英语） |
| 目标语言 | 由你在对话里点名（「日译中」「翻成繁中」「译成英文」），不点名默认简中 |
| 模型 | 跟随 DSH「设置 → 模型」里的默认线路，当前是 `deepseek-official / deepseek-flash` |
| 批次 | 行数/字数/回复预算三者取最小，默认 8 并发，重试 2 次，错行时二分拆批 |
| 输出位置 | 永远写在输入文件旁边 |

保存的值落在 `~/.dsh/mtool-translate/settings.json`，改完下次翻译立即生效；点「恢复默认」清掉覆盖。也可以在对话里说「推理开 high」，助手用 `mtool_translate_config` 写同一个文件。

YAML 里只有这一项可配：

```yaml
- id: mtool-translate
  config:
    reasoningEffort: low
```

### 消费报告

每次翻译的返回里多了一段账单：

```
Cost: 1 request(s) · 1/1 batch(es) of ≤200 line(s)
Tokens: in 3,600 (2,176 cached · 60.4%) · out 6,420 · total 10,020
Per line: in 18.0 · out 32.1 · 8.1 lines/s
Per request: in 3600 · out 6420 · 24.6s
```

- **request(s)**：真实发出去的请求数。它大于批次数，说明钱花在重试和补行上。
- **batch(es) of ≤N line(s)**：本次计划把每请求压到几行以内——行数上限、字数上限、回复预算，以及"让 8 个并发都不闲着"四者取最小。这个数比设置里的「批次行数」小，通常是并发分摊或回复预算在起作用。
- **truncated**：回包的结束原因是撞到 token 上限而非正常收尾。出现它说明批宽已经超过回复预算，下一轮该调小——它是宽批唯一会静默丢行的地方，所以单独计数。
- **cached**：路由上报的 `inputTokens` 是**未命中缓存的部分**，`cacheReadTokens` 才是命中的部分，报告里的 `in` 是两者之和（实测 311 + 3,454 = 3,765 对上同一次请求的 total，以此定案）。同前缀原样重发实测 91.7% 命中，说明这条链路是通的；换成新内容跑时只有稳定前缀（系统提示两百来字）会命中，比例会低得多。
- **reasoning**：这条线路恒为 0 —— **思考量被并入 `outputTokens`，没有单独上报**。所以要看思考成本就比每行输出：实测同一份文本，`low` 是 32–48 token/行（同一内容重跑也能差一半），`off` 是 12.6 token/行、26 行/s。**`low` 贵 3–4 倍、慢 5 倍，几乎全是思考量。**

  由此得出一个和直觉相反、但数据支持的结论：**批宽不是成本的杠杆。** 思考量跟着内容走、不跟请求数走——200 行塞进一次请求是 32.1 token/行，拆成两批是 46.3 token/行，差异落在噪声里。批宽真正省下的是每请求那点固定开销（系统提示两百来字）和往返次数，不是思考费。**要省钱只有换档位，要稳只有统一术语，这两件事和批宽都无关。**
- 全部命中本地缓存的重跑只输出一行 `no model request this call`。

只报 token 不报钱：插件看不到线路的价目表。

### 增量缓存

`.mtool-translate-cache.json` 是逐行对照表（`sha1(目标语言+原文) → 译文`），写在导出文件旁边，**始终开启**。它只影响「下次再翻同一份/同一目录」，不影响 MTool 加载。翻完确认没问题后手动删掉即可——名词表也存在这个文件里，会一起清掉；留着的话下次打补丁重导出只为新增行付钱。注意它保存了译文原文，分享游戏目录时会一起带出去。

## 名词表

同一部游戏里人名/地名/道具名前后不一致，是因为模型是按批次独立翻的。名词表就是治这个的：**每个游戏一份，建好之后每次翻译自动带上**。

- **建表**：让助手「先抽一下名词表」，它调 `mtool_translate_glossary` 的 `build`——从导出文本里抽高频片假名和「××さん/様/殿」这类称呼，让模型给统一译名，约 40 条，一次调用。
- **过目**：抽完会把清单打给你。不满意的让助手改（`set`）或删（`remove`），例如「把 アイテム、エリア、ベッド 这几条去掉」。
- **自动生效**：之后 `translate_mtool_file` 每次都会加载这张表，结果里会显示 `Glossary: N term(s) applied`。
- **存哪儿**：就直接放在游戏目录的 **`.mtool-translate-cache.json` 里**（和译文缓存同一个文件，按目标语言分块）。选择这样是因为你只需要容忍一个残留文件：删掉 cache = 缓存和名词表一起清干净，不留别的。
- 单次调用也可以用 `glossary` 参数临时补几条，优先级高于表里的同名词条。

## 风格简报

术语可以靠表约束，文风不行——8 条流各自开写，语气、人称、称呼习惯会各走一路，而这些问题**不是错，是味道不齐**，审计抓不到。

- **一次调用换一个共同前提**：`mtool_translate_style` 的 `build` 会从整份文件里**均匀抽样** 240 行（不是取开头一段，否则简报只代表第一个场景），让模型写一份 300 字以内的翻译政策：类型与氛围、人称与叙事、语气与尺度、称呼习惯（さん/ちゃん/様/君 各自怎么处理）、抽样里反复出现的专有名词首选译法、格式约定。
- **自动生效**：之后 `translate_mtool_file` 每次都会把它拼进系统提示的 `###翻译风格` 段，结果里显示 `Style: brief applied (N chars)`。
- **存哪儿**：还是 `.mtool-translate-cache.json`，`style` 块按目标语言分开——和名词表、译文缓存同一个文件，删 cache 一起清掉。
- **可改可删**：`show` / `set`（直接给正文，覆盖模型的措辞）/ `remove`。
- 简报要短。它会被拼进**每一个**请求，300 字约 300 token，26 个请求就是 8k token——比它买到的文风一致性便宜得多，但别写成一千字。

实测：一部 5049 行的游戏，抽样 240 行、一次纯输入调用，产出约 300 字简报。

## 一致性审计

名词表负责**翻译前**给出决定；审计负责**翻译后**核对决定有没有被遵守。两者不能互相替代——表再全也只是预测，漂移只有落在译文里才看得见。

- **随时可查**：`mtool_translate_consistency`（`action: report`，默认）不花模型调用。它把译文里每个片假名串、敬称名、引号内短串，以及所有汉字组合都当候选（片假名/敬称/引号出现 2 次即入选，汉字 n-gram 要 3 次且必须**落在词边界上**——只在更长汉字串里出现的片段不算，`面座位` 之于 `対面座位`），再看这些词在译文里有没有统一写法。
- **以表为基准**：名词表里已经钉住的词**按表核对**——列出「这行没照表写」的行，而不是去统计多数。没在表里的词才退回按多数找漂移。这条很重要：`設定` 在 19 行里 14 行写成"变量"（错译），按多数看它"很一致"，按表看它是 14 行违规。
- **顺手就报**：`translate_mtool_file` 每跑完一次都会附一行 `Consistency:`，告诉你有几个候选词漂了、是哪几个。没漂就是 `every rendering agrees`。
- **第二遍：判断，而不是投票**（`action: revise`）。对**不在表里**的冲突簇，问模型「哪个译法更好」——不是「哪个出现得多」；答案可以是少数派、可以是新译法、也可以 `keep`（这个词在某行里只是更长的一个词的一部分，或中文里本来就该换说法）。**表里已有的词不再判断，直接执行**：表是契约，一次运行不能把自己说服。
- **判断请求 4 路并发**：19 个词是 4 个请求同时发，不是 19 次排队。
- **重的不是替换，是重写**：选定的行**重新翻译**（照常遮蔽控制码、逐行校验占位符和换行数），不是把片段剪贴过去。剪贴改不了句子，重写能。
- **沉淀成表**：选定译法写进游戏的 `.mtool-translate-cache.json` 名词表，下次翻译第一遍就一致——**这就是"表从译文里长出来"**，覆盖问题自动消失，因为它从实际译文抽，不受频次门槛限制。
- **不会回退**：改过的行同步写回译文缓存，`force` 重跑不会把旧译法带回来。
- **有收口证明**：修完会再跑一遍确定性审计，用「剩余漂移数」告诉你还剩几个。

实测：3517 行译文、385 个候选、119 个报漂移、耗时 69ms（不花模型调用）。

**已知边界**：确定性这半能指出「哪几行不一致」，但不能可靠指出「错的是哪个词」——所以报告给的是偏离行的整句译文，由模型在 revise 时判断。复合词（`コキ` 之于 `手コキ`/`足コキ`）和中文省主语都会进报告，靠 `keep` 挡掉。另外「两个不同原词被译成同一个词」不在检测范围内。

## 限制

- 只处理 MTool 导出的 JSON 格式（扁平 `原文: 译文`）。T++ 的 `.trans`、Ren'Py 的 `.rpy` 不在范围内。
- 运行时抓取（MTool 的 hook）不在范围内：本插件只做「文件进、文件出」，游戏仍需用 MTool 挂载译本。
- 译文长度不会自动适配窗口宽度；某行溢出就在 MTool 的翻译修正里改。
- 模型仍可能译错；插件保证的是**格式、控制码、行数不出错**，不是语义正确。

## 自检

```bash
node smoke.mjs
```

用桩 LLM 覆盖控制码遮蔽/还原、跳过规则、回包解析、逐行校验、符号修复、缓存、重试、断点续跑，不需要网络。
